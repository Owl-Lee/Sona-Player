# Sona 项目技术亮点与讲解

> 用途：帮助我自己真正理解这个项目，也作为后续开发、GitHub README、作品集和面试讲解的底稿。
>
> 原则：只把已经完成并验证过的功能说成“已实现”；仍在规划、开发或测试中的内容必须明确标记。

---

## 1. 一句话介绍

**Sona** 是一个以 Windows 和 Android 为主力平台的私人音乐播放器：用户可以导入自己拥有的 MP3、FLAC、M4A、WAV 等音乐文件，在电脑上整理曲库和歌单，在手机上登录同一个账号后播放、缓存并同步数据。

它可以理解成一个属于自己的、离线优先的网易云音乐或 Spotify，但不依赖平台会员，也不负责提供版权音乐。

当前项目状态：**0.3.0 多巴胺外观与 MV 版已完成 Windows Release 与 Android APK 构建：修复重复更换背景失效，加入按窗口比例拖动/缩放裁切、全局背景、五套明亮皮肤、新黑胶素材、MP4/MV 导入与视频渲染、歌单名称/描述/封面编辑以及精细音量控制。Android SDK、自定义路径、JDK 和许可证均已配置，代码静态检查与自动测试通过；为避免打扰用户，本轮没有弹出播放器或模拟器做真实窗口测试。云同步仍在后续阶段。**

---

## 2. 为什么要做这个项目

现有在线音乐平台虽然方便，但也有几个现实问题：

- 账号可能被别人使用或影响推荐记录；
- 很多歌曲需要会员；
- 平台上的歌曲可能突然下架；
- 自己下载的音乐文件不好在多台设备之间管理；
- 换手机后，本地曲库、歌单和播放记录通常需要重新整理；
- 用户很难真正控制播放器的外观、数据和文件。

这个项目的核心不是简单做一个“能播放 MP3 的页面”，而是把下面三件事整合起来：

1. 本地音乐播放器；
2. 跨设备曲库管理系统；
3. 私人云端同步服务。

## 3. 项目范围

### 第一阶段的主力平台

- **Windows：** 导入歌曲、批量整理、编辑歌单、查看完整曲库；
- **Android：** 日常播放、后台播放、锁屏控制、缓存和离线收听；
- **macOS：** Flutter 架构会尽量保持兼容，后续有余力再打包和测试；
- **iPhone / iOS：** 第一阶段暂不开发。

iOS 并不是技术上完全做不了，而是个人安装和发布会涉及 macOS 构建环境、代码签名、开发者证书、设备授权以及 App Store 审核。为了先做出真正能用的版本，第一阶段不把时间消耗在苹果发布流程上。

## 4. 整体技术架构

推荐使用一套代码同时覆盖 Windows、Android 和后续 macOS：

```text
                    ┌─────────────────────────────┐
                    │       Flutter 客户端        │
                    │ Windows / Android / macOS   │
                    └──────────────┬──────────────┘
                                   │
                 ┌─────────────────┴─────────────────┐
                 │                                   │
        ┌────────▼────────┐                 ┌────────▼────────┐
        │ 本地 SQLite 数据库 │                 │   云端服务层     │
        │ 曲库/歌单/缓存状态 │                 │ 登录/同步/权限   │
        └────────┬────────┘                 └────────┬────────┘
                 │                                   │
        ┌────────▼────────┐          ┌───────────────┴───────────────┐
        │  本地音乐文件    │          │                               │
        │  本地缓存文件    │  ┌───────▼────────┐            ┌────────▼────────┐
        └─────────────────┘  │ Supabase       │            │ Cloudflare R2  │
                             │ 账号/PostgreSQL │            │ 音频/封面文件   │
                             └────────────────┘            └─────────────────┘
```

### 推荐技术栈

| 位置 | 推荐技术 | 作用 |
| --- | --- | --- |
| 客户端 | Flutter + Dart | 一套代码开发 Windows、Android 和 macOS |
| 播放内核 | media_kit | 播放多种音频格式，兼顾桌面端和移动端 |
| Android 后台播放 | audio_service | 通知栏、锁屏、耳机按钮和后台媒体会话 |
| 本地数据库 | SQLite + Drift | 保存离线曲库、歌单、任务和同步状态 |
| 状态管理 | Riverpod | 管理播放器状态、账号状态和页面数据 |
| 账号与云数据库 | Supabase Auth + PostgreSQL | 登录、用户数据、歌单和同步记录 |
| 权限控制 | Supabase RLS | 限制每个账号能看到和修改的数据 |
| 音频对象存储 | Cloudflare R2 | 存放 MP3、FLAC、封面等大文件 |
| 文件身份识别 | SHA-256 | 识别相同文件，防止重复上传 |

这套方案的重点是：**数据库负责管理信息，对象存储负责保存大文件。**

不要把几千首 MP3 直接塞进 PostgreSQL。数据库更适合保存歌曲名称、歌手、专辑、文件哈希、对象路径、上传时间等结构化信息；真正的音频字节应该放在 R2 这类对象存储中。

## 5. 从导入一首 MP3 到手机播放，背后发生了什么

这是整个项目最重要的一条数据流程。

```text
Windows 选择音乐文件
        ↓
读取 ID3 标签、时长、格式、码率和内嵌封面
        ↓
计算 SHA-256 文件哈希
        ↓
检查本地和云端是否已经存在同一文件
        ↓
把歌曲写入本地 SQLite，电脑可以立即播放
        ↓
后台向服务端申请短期有效的上传地址
        ↓
音频文件直接上传到私人 R2 存储桶
        ↓
PostgreSQL 保存歌曲元数据和 R2 对象路径
        ↓
Android 登录同一账号并增量同步曲库
        ↓
有本地缓存就直接播放；没有则申请临时播放地址
        ↓
边播放边缓存，或完整下载后离线播放
```

### 为什么要读取 ID3 标签

MP3 等音乐文件通常不只有声音，还可能包含：

- 歌名；
- 歌手；
- 专辑；
- 曲目编号；
- 年份；
- 音乐类型；
- 专辑封面。

播放器导入文件时应优先读取这些标签，而不是只使用文件名。标签缺失时，再从文件名推断或让用户手动编辑。

### 为什么要计算 SHA-256

同一首歌可能存在于不同文件夹，也可能被改过文件名。路径和文件名都不可靠，而文件内容哈希更适合作为文件身份。

例如：

```text
D:\Music\周杰伦\晴天.mp3
E:\Backup\Jay - 晴天.mp3
```

如果两个文件的 SHA-256 相同，就可以判断它们实际上是同一份音频，不必重复上传。

但“同一首歌的不同音质版本”会产生不同哈希，因此数据库还需要区分歌曲概念和具体音频文件。后续可以让一首歌曲关联 128 kbps MP3、320 kbps MP3、FLAC 等多个版本。

## 6. 本地优先，而不是必须联网

这个播放器不应该因为网络断开就完全失效。

本地 SQLite 至少需要保存：

- 已导入的歌曲信息；
- 本地文件路径；
- 已下载文件路径；
- 歌单和歌曲顺序；
- 收藏状态；
- 最近播放记录；
- 播放进度；
- 待上传、待修改和待删除的同步任务；
- 最近一次云端同步游标。

本地操作应先立即生效，再在有网络时同步到云端。

```text
用户点击“收藏”
        ↓
本地数据库立即写入，界面马上变化
        ↓
生成一条待同步任务 Outbox
        ↓
有网络时上传到云端
        ↓
服务端确认后标记任务完成
```

这种设计叫 **Offline-first（离线优先）**。它比所有按钮都等待服务器响应更适合音乐播放器。

## 7. 账号、密码和登录系统是怎么实现的

登录页面本身并不难，真正重要的是后面的身份验证和权限控制。

### 注册

1. 用户输入邮箱和密码；
2. 客户端通过 HTTPS 把注册请求发给 Supabase Auth；
3. 服务端使用安全哈希算法处理密码；
4. 数据库只保存密码哈希，不保存明文密码；
5. 注册成功后，为用户创建个人资料和默认曲库。

### 登录

1. 用户提交邮箱和密码；
2. 服务端验证密码；
3. 验证成功后返回 Access Token 和 Refresh Token；
4. 客户端安全保存令牌；
5. 后续请求通过令牌证明“我是谁”。

Access Token 通常有效期较短，Refresh Token 用来换取新的 Access Token。这样即使某个短期令牌泄露，风险也比永久密码小。

### 权限控制

仅仅在客户端隐藏别人的歌曲远远不够。真正的权限必须在数据库和服务端执行。

Supabase 的 RLS（Row Level Security，行级安全）可以表达这样的规则：

```text
用户只能读取自己拥有的曲库
或者
用户只能读取自己被邀请加入的共享曲库
```

即使有人绕过客户端直接调用接口，数据库仍然会拒绝越权请求。

## 8. 云端应该保存什么

### PostgreSQL 保存结构化数据

初步计划的数据表如下：

| 数据表 | 主要内容 |
| --- | --- |
| profiles | 用户昵称、头像和个人设置 |
| libraries | 曲库名称、拥有者和创建时间 |
| library_members | 共享曲库中的成员和权限 |
| tracks | 歌名、歌手、专辑、时长、哈希和对象路径 |
| playlists | 歌单名称、封面、创建者和排序方式 |
| playlist_items | 歌单中有哪些歌曲以及歌曲顺序 |
| favorites | 每个用户收藏了哪些歌曲 |
| play_history | 播放记录、次数和最后播放时间 |
| devices | 登录过的电脑和手机 |
| change_log | 用于增量同步的数据变更记录 |

### R2 保存二进制文件

- MP3；
- FLAC；
- M4A；
- WAV；
- 专辑封面；
- 用户自定义背景。

R2 存储桶应设为私有，不能把所有音乐暴露成永久公开链接。

客户端需要播放歌曲时，服务端根据登录身份签发一个短期有效的 Signed URL。链接过期后自动失效，可以减少文件被随意传播的风险。

R2 的密钥只放在受控的服务端环境中，绝不能直接写进 Windows 或 Android 安装包。

## 9. 多设备同步为什么是难点

账号系统不等于同步系统。

真正困难的情况包括：

- 电脑离线时创建了歌单，手机也离线修改了同一个歌单；
- 电脑删除歌曲时，手机还保留旧数据；
- 文件上传到一半网络断开；
- 手机只下载了歌曲的一部分；
- 同一文件被多台设备同时上传；
- 用户在设备 A 退出账号后，设备 B 仍在使用旧令牌。

### 初步同步策略

1. 每条重要记录包含 `updated_at` 和版本号；
2. 删除记录时先写入 `deleted_at`，而不是马上彻底删除；
3. 客户端保存同步游标，只拉取上次同步后发生的变化；
4. 本地修改进入 Outbox，按顺序重试；
5. 上传文件支持断点续传或分片上传；
6. 简单字段冲突先使用“较新版本优先”；
7. 歌单顺序等复杂冲突后续单独设计。

`deleted_at` 这种做法叫软删除或 Tombstone。它能让其他设备知道“这条数据已经被删掉”，避免被旧设备重新同步回来。

## 10. Windows 和 Android 的分工

### Windows 是主曲库管理端

电脑导入 MP3 最方便，因此 Windows 端适合承担：

- 拖拽文件和文件夹导入；
- 批量扫描音乐目录；
- 监控指定文件夹的新文件；
- 批量修改歌曲信息；
- 查重和整理重复文件；
- 创建大型歌单；
- 执行云端上传任务；
- 导出曲库备份。

后续可以增加“监控音乐文件夹”：用户把新歌曲下载到指定目录，播放器自动发现、解析并询问是否加入曲库。

### Android 是随身播放端

Android 端适合承担：

- 浏览和搜索曲库；
- 日常播放；
- 蓝牙耳机按键控制；
- 锁屏和通知栏控制；
- Wi-Fi 下自动缓存；
- 指定歌单完整离线下载；
- 展示同步和下载进度。

Android 后台播放不是让一个页面一直开着，而是要建立系统认可的媒体服务和媒体会话。这样切到其他应用或锁屏后，音乐才不会被轻易停止。

## 11. 三种播放方式

### 1. 本地播放

歌曲已经存在于电脑或手机中，直接读取本地文件。速度最快，也不消耗网络。

### 2. 在线串流

歌曲只存在云端，客户端通过短期链接边下载边播放。适合临时听歌，但网络不稳定时可能卡顿。

### 3. 离线下载

把完整歌曲下载到应用管理的缓存目录，并记录缓存状态。即使没有网络也能播放。

计划提供三种用户模式：

- 仅串流；
- 智能缓存；
- 指定歌曲或歌单永久离线。

缓存需要有清理策略，例如限制最大空间、优先清理很久没播放的歌曲，并且绝不能误删用户原始音乐文件。

## 12. 自定义播放器样式怎么做

“自定义”不应该等于把所有页面逻辑重写一遍。更合理的设计是把播放器拆成数据、控制和外观三层：

```text
播放内核：负责真正播放音频
        ↓
播放器状态：当前歌曲、进度、队列、播放模式
        ↓
播放器皮肤：封面布局、按钮样式、颜色、背景和动画
```

只要皮肤通过统一接口读取播放器状态、发送播放命令，就可以在不更换播放内核的情况下切换样式。

0.2.0 已经把这套分层落到了代码中：

- 曲库使用浅色、紧凑、适合大量歌曲浏览的布局；
- 完整播放器单独进入沉浸式页面，不让花哨背景干扰曲库阅读；
- 黑胶和唱臂使用 Flutter `CustomPainter` 绘制，播放时由 `AnimationController` 驱动唱片持续旋转；
- 内置“极光夜、樱花暮色、晴海、霓虹雨”四套原创背景；
- 用户可从本机导入自己的图片，程序会复制到声仓应用数据目录；
- 当前皮肤写入 SQLite `settings` 表，重启后仍然保留；
- 背景统一叠加深色可读性遮罩，避免浅色海面或高亮区域吃掉白色文字；
- 同一播放页在宽屏时使用“唱片 + 信息”双栏布局，窄屏时改为纵向布局。

目前没有做完全自由拖拽的播放器设计器。先把“背景可换、信息不乱、唱片好看、控制完整”做稳，比让用户随意拖坏布局更适合第一阶段。

## 13. 可以加入的项目亮点

### 亮点一：用内容哈希识别歌曲文件

歌曲不会因为移动文件夹或修改文件名就变成另一首，能够减少重复上传和重复记录。

### 亮点二：本地优先的同步体验

没网时仍能整理歌单和播放已缓存音乐，恢复网络后自动补同步。

### 亮点三：电脑作为主曲库

Windows 负责方便地导入和整理，Android 负责随身播放，符合真实使用习惯。

### 亮点四：局域网优先传输

如果电脑和手机位于同一个 Wi-Fi，后续可以让手机直接从电脑下载歌曲，不经过云端。

```text
同一局域网：Windows → Android
不在同一网络：R2 → Android
```

这样既能加快传输，也能减少云端读取请求和带宽消耗。

### 亮点五：共享曲库和个人数据分离

以后可建立家庭共享曲库，多账号共同使用同一批音频文件，但每个人保留自己的：

- 收藏；
- 播放记录；
- 最近播放；
- 私人歌单；
- 推荐统计。

### 亮点六：同步状态透明

播放器应明确显示：

- 仅本地；
- 等待上传；
- 正在上传；
- 已同步；
- 已缓存；
- 同步失败；
- 需要处理冲突。

## 16. 最难的技术点

这个项目看起来像播放器，实际难点主要在工程细节。

### 1. Android 后台播放

需要处理系统媒体服务、通知栏、锁屏、音频焦点、耳机事件以及被系统回收后的恢复。

### 2. 大文件稳定上传

不能因为网络断开就从零重新上传一个几百 MB 的文件，需要进度、重试、断点续传和失败恢复。

### 3. 离线同步冲突

两台设备都能离线修改数据，就必须定义谁覆盖谁、删除如何传播以及任务如何重试。

### 4. 文件和数据安全

需要 RLS、私有存储桶、短期签名链接、HTTPS、令牌刷新和服务端密钥隔离。

### 5. 大曲库性能

几千首歌曲不能一次全部加载到界面，需要数据库索引、分页、虚拟列表、封面缩略图和懒加载。

所以“做出能播放一首歌的 Demo”很快，“做成每天都敢用的软件”才是这个项目真正的价值。

## 19. 面试或项目讲解时可能被问到的问题

### 为什么选择 Flutter

因为目标平台同时包含 Windows 和 Android，并希望后续兼容 macOS。Flutter 可以共享大部分界面、业务逻辑和数据模型，同时保留调用平台原生能力的入口。

### 为什么不用一个数据库直接存 MP3

音频属于大体积二进制对象，放进关系数据库会增加数据库体积、备份压力和传输成本。数据库保存元数据，对象存储保存文件，更容易扩展和维护。

### 为什么本地还需要 SQLite

因为音乐播放器必须在无网时工作。SQLite 既保存本地曲库，也充当云端数据的本地缓存和待同步任务队列。

### 怎么避免重复上传

导入时计算文件 SHA-256，先在本地和云端查询哈希；同一账号或同一共享曲库已经有相同文件时，只建立数据关联，不再次上传。

### 云端歌曲怎样防止别人直接下载

存储桶保持私有；用户登录后，由受信任的服务端根据权限签发短期 Signed URL；数据库通过 RLS 限制元数据访问；R2 密钥不进入客户端。

### 为什么同步比登录难

登录主要解决身份问题，同步还要面对多设备、离线修改、删除传播、版本冲突、失败重试和大文件传输。

### 云服务会不会很贵

个人规模下，账号和元数据可以放在 Supabase 免费层，音频放 R2。大约 10 GB 以内可能保持免费，超过后按实际存储量低价计费；正式上线前仍需重新确认价格和用量。

## 20. 约 60 秒的项目介绍

我正在开发一个名为“声仓 SonarVault”的 Windows 和 Android 私人云音乐播放器。Windows 端负责导入和整理用户自己的 MP3、FLAC 等文件，Android 端负责日常播放、后台控制和离线缓存。客户端使用 Flutter，本地使用 SQLite 保存曲库和歌单；云端后续使用 Supabase 处理账号、PostgreSQL 数据和权限，音频大文件放在 Cloudflare R2。

### 2026-08-14：0.2.0 外观大改与黑胶播放器

#### 需求来源

- 曲库页面浅色、信息密度高、歌曲行紧凑；

- 播放背景可以表达情绪，但不能影响歌名、进度和按钮的识别。

#### 为什么歌词先不做

本地 MP3 没有歌词时，播放器不能凭空得到可靠的逐行时间轴。完整的歌词链路至少需要：

```text
歌名 / 歌手 / 专辑 / 时长
        ↓
联网搜索多个歌词版本
        ↓
判断哪个版本和当前音频一致
        ↓
读取 LRC 时间轴或重新对齐
        ↓
用户校对错误结果
```

AI 语音识别可以作为“歌词草稿”工具，但歌曲里存在伴奏、和声、方言、混响和重复段落，自动结果不一定准；识别出文字也不等于每句时间轴就准确。因此 0.2.0 不显示假歌词或空歌词页，先把纯 MP3 播放做好。

#### 新的界面结构

```text

├─ 本地曲库：搜索 + 全部/收藏/有 MV + 紧凑歌曲表
├─ 歌单
└─ 设置与外观
        ↓ 点击底部歌曲信息
沉浸式播放器
├─ 唱片模式：旋转黑胶 + 唱臂
├─ MV 模式入口：显示配对状态
├─ 播放进度和完整控制
└─ 四套内置背景 + 用户自定义背景
```

桌面宽屏使用左侧导航和底部完整控制栏；窄屏使用底部导航和圆角迷你播放器。完整播放页在宽屏为左右双栏，在窄屏为纵向布局，并同时根据窗口高度缩小唱片，避免控制按钮被推到屏幕外。

#### 黑胶和唱臂怎样实现

黑胶不是一张固定 PNG，而是代码绘制：

- `CustomPainter` 绘制黑胶外圈、同心纹路、反光和中心孔；
- 中央唱片标签复用歌曲的动态封面色块；
- 另一层 `CustomPainter` 绘制唱臂、转轴和唱头；
- `AnimationController` 每 16 秒转一圈；
- 播放时继续旋转，暂停时停在当前位置，不会突然跳回 0 度。

代码绘制的好处是任何分辨率都清晰，桌面和手机不需要各存一套唱片图片，也能方便修改尺寸、速度和颜色。

### 2026-08-14：0.3.0 多巴胺外观、背景裁切与 MV 真播放

#### 这一轮解决了什么

本轮来自第一次真实使用反馈，重点不是继续堆页面，而是修复会直接影响日常使用的问题：

- 自定义背景连续更换几次后不再刷新；
- 自动居中裁切会把人物或画面主体切掉；
- 原四套背景偏暗，主界面和播放器没有形成统一视觉；
- 黑胶中心出现歌曲标题中的 `《`，既不像封面，也不像品牌标志；
- 播放器右上角三点按钮没有行为；
- 音量条太短、时间太小，无法精确控制；
- 文件导入器只能看到音频，不能导入独立 MP4/MV；
- 歌单只能创建和删除，不能修改名称、描述与封面。

#### 为什么背景换几次后会“卡死”

旧实现每次都覆盖同一个文件：

```text
custom_player_background.jpg
```

但 Flutter 的 `FileImage` 会把文件路径作为缓存键。文件内容虽然变了，路径没有变，界面仍可能继续使用旧的内存缓存，因此用户会感觉按钮失效。

0.3.0 改为每次生成唯一文件名：

```text
custom_时间戳.jpg
```

路径变化后缓存键也变化，界面必然重新解码新图。这比依赖手工清除全局图片缓存更安全，因为清空全局缓存可能让其他正在显示的图片一起闪烁或重新加载。

#### 背景裁切怎样适配电脑和手机

选图后不再立即保存，而是进入裁切页：

1. 读取当前播放器窗口的宽高；
2. 用 `宽 ÷ 高` 计算裁切框比例；
3. 固定矩形裁切框，保证保存结果能铺满当前播放器；
4. 用户拖动图片决定主体位置；
5. 用户通过触摸手势或鼠标滚轮缩放；
6. 确认后才把裁切结果保存到应用数据目录。

裁切由纯 Flutter 组件 `crop_your_image` 完成，因此 Windows 和 Android 共用同一套交互。歌单封面复用同一个裁切组件，只把比例改成 `1:1`，没有再写第二套图片处理逻辑。

这里有一个现实边界：电脑横屏裁出的图不一定是手机竖屏最理想的构图。当前版本按“正在使用的设备”裁切；后续云同步阶段可以为同一背景保存桌面版和手机版两个裁切结果。

#### 为什么播放器仍需要一点遮罩

完全不加遮罩时，白云、海面反光和浅粉樱花会直接吃掉白色歌名与按钮；统一压得很黑，又会失去用户想要的多巴胺颜色。

0.3.0 使用分层方案：

- 原图保持本来的色相，不做黑色偏色滤镜；
- 每套皮肤拥有自己的轻量遮罩强度；
- 播放器只增加约四分之一到三分之一的中性黑色透明层；
- 主界面使用高透明白色雾面层，既能看见背景色，又保持曲库表格可读；
- 左侧导航从当前皮肤提取强调色，用浅色混合，而不是固定蓝色。

这相当于让“背景负责情绪、雾面负责可读性、强调色负责统一”，避免背景和内容互相抢夺。

| 默认白 | 白色到浅灰蓝，最安静 | 珊瑚红 |

#### 黑胶为什么从代码绘制改成原创位图

0.2.0 的代码黑胶便于响应式缩放，但真实感不足：沟槽密度、边缘厚度、材质高光都显得像简单图形。0.3.0 保留 Flutter 控制的旋转动画与唱臂，同时将唱片主体换成原创高分辨率黑胶素材：

- 细密同心沟槽；
- 低调的彩色光谱反射；
- 温暖象牙白的无字中心标签；
- 不显示歌曲文件名的第一个标点；
- 播放继续旋转，暂停停在当前位置。

曲库里的自动封面也加入了字符清洗：标题为 `《K歌之王》` 时，会跳过书名号并选择 `K`；没有可用字母、数字或汉字时才显示音乐符号。

#### MP4 / MV 是怎样接通的

依赖由“仅音频运行库”切换为 `media_kit` 的视频运行库。官方说明中，视频运行库同时覆盖音频和视频，所以不能把 audio 和 video 两套原生库混装。

数据库升级到版本 3：

```sql
ALTER TABLE tracks ADD COLUMN media_type TEXT NOT NULL DEFAULT 'audio';
```

导入器现在同时识别：

```text
音频：MP3 / FLAC / M4A / WAV / OGG / Opus / AAC / AIFF / APE
视频：MP4 / MKV / MOV / WebM / AVI
```

有两种数据形式：

- **MP3 + MV：** `path` 指向音频，`video_path` 指向配对视频；
- **独立 MV：** `path` 和 `video_path` 都指向视频，`media_type = video`。

播放器的唱片模式和 MV 模式共用同一个播放时钟、进度条、音量和队列。切换来源时会尽量保留当前进度，并把当前曲目在队列中的位置保留下来。独立 MV 打开完整播放器时会自动进入视频模式。

本轮已经完成视频组件接线并通过 Windows Release 编译；由于遵守“开发时不要反复弹窗口”的要求，没有在用户桌面上自动播放私人 MP4，因此不同编码文件的声音、画面与进度同步仍需要下一轮用用户自己的样本做一次手动验收。

### 播放队列、歌单批量管理与全局皮肤（0.3.1 开发中）

播放器不再把“循环”含糊地理解为最近播放，而是引入了明确的**当前播放队列**：从本地曲库、收藏、搜索结果、最近播放或某个歌单点歌时，会把当时可见的列表复制成一份队列快照，同时记录来源。离开页面或改变搜索条件不会突然改动正在播放的队列。

播放模式统一为三种：

- 列表循环：当前队列末尾接回第一首；
- 单曲循环：只重复当前歌曲；
- 随机播放：在当前队列中随机播放。

#### 账号、头像、排行与设置上传云端是否可行

可行，而且这些结构化数据比上传音乐文件简单得多。推荐拆成两层：

1. 账号层：使用 Supabase Auth 一类成熟身份服务处理邮箱/密码登录。客户端和数据库都不保存明文密码，只保存服务颁发的登录令牌；用户表保存昵称、头像地址和公开 ID。
2. 同步层：云端 PostgreSQL 保存歌单、收藏、歌曲元数据、播放事件、主题设置和设备同步游标；头像放对象存储。每张表都带 `user_id`、更新时间和删除标记，并通过行级权限保证只能读取自己的数据。

播放次数、头像、账号资料、歌单和设置数据量很小，免费额度通常足够个人开发测试。真正昂贵的是 MP3/MV 文件：它们体积大，还涉及上传流量、下载流量、重复文件去重和版权责任。因此第一阶段建议只同步账号与结构化数据；音频云盘另用 R2/S3 兼容存储，并让用户明确只上传自己有权保存的文件。

多设备同步不能只做“整库覆盖”，否则电脑和手机同时修改会丢数据。应使用事件或增量同步：播放记录按事件追加，收藏按最后更新时间合并，歌单项目使用独立记录和软删除，设置按字段更新时间解决冲突。这样以后接云不会推翻当前本地数据库。

### 0.3.4 设计确认清单：唱片、液态玻璃、有效播放与低成本云同步

本轮先记录和确认规则，不立即改代码。下一轮统一实现，避免界面与数据规则反复返工。

#### 已确认需要改动的界面与交互

- 重做唱片与唱臂视觉。当前唱臂的转轴、弯折和唱针落点不自然，下一版不继续修补现有合成图，而是制作一套原创、结构正确的高质感唱片素材；唱臂应从唱机右上方转轴自然伸向唱片外圈，不能像贴歪的白色图形。
- MV 画面本身成为播放控制区：单击视频暂停，再单击继续；拖动进度条、双击等手势要与单击区分，避免误触。
- 搜索框、筛选框、播放器信息面板、临时音量条统一采用轻量液态玻璃语言：半透明材质、细亮描边、内高光、柔和阴影、主题色折射。液态玻璃只用于重要控制层，不把所有内容卡片都做成玻璃。
- 自定义背景不再因为切换到内置皮肤而消失。导入结果进入“我的背景”持久列表，只有用户主动替换或删除才移除；默认先保留最近 5 张，后续可增加数量管理。
- 放大全屏播放器控制键并重新分配间距。主播放键最醒目，上一首、下一首、模式、队列、收藏和音量形成清晰层级；主播放键和音量激活态跟随当前主题强调色。
- 只有全屏播放器使用竖向液态玻璃音量条；底部常驻播放器继续保留横向音量条和百分比，不改变已经顺手的桌面操作。
- 首页标题旁的“曲库 248.5 MB”改成独立的小型数据胶囊，增加图标、边框和层级，不再把容量作为一段突兀的行内文字。

苹果的材料设计说明强调：Liquid Glass 是浮在内容之上的功能层，用于控件与导航，并不适合铺满内容层；它会根据下方内容和环境自适应，同时必须优先保证可读性。因此 Sona 会借鉴它的层级、透光、描边和响应感，而不是机械复制一个高开销的全屏实时模糊。MV 播放时尤其要限制模糊范围，避免重新引入卡顿。

#### “播放一次”不能等于“点了一下”

当前在开始播放时立刻增加次数，会让连续点击、试听几秒和误触污染排行。建议改成统计**实际听过的时间区间**，而不是看进度条最终走到了哪里：

- 普通音频或 MV（不超过 10 分钟）：实际覆盖达到全长 50%，且至少听满 30 秒，才记 1 次；
- 长视频或长音频（超过 10 分钟）：实际播放满 5 分钟，记 1 次；
- 从中间开始允许计数，但跳到 80% 不会立刻算一次，只有后续真实播放的区间才累计；
- 暂停期间不累计，来回拖动经过同一段不重复增加覆盖时长；
- 同一次播放会话最多记 1 次，播放结束后重新开始才可能产生下一次；
- 周榜、月榜和总榜都只读取这些“有效播放事件”。

50% 比 70% 更适合私人播放器：大多数人会跳过前奏、片尾或在歌曲将结束时切歌；70% 更像“完整听完率”，容易漏记真实喜欢的歌曲。若以后想看得更细，可以同时保留“有效播放次数”和“完整听完次数”，但第一阶段只做前者。

#### 低成本云同步方案

账号、头像、歌单、收藏、播放事件和设置都能同步，而且体积很小。推荐第一阶段采用 Supabase：

- Supabase Auth 管理邮箱和密码登录；Sona 不保存、更不会上传明文密码；
- PostgreSQL 保存用户资料、歌曲元数据、歌单、歌单项、收藏、有效播放事件、主题设置和同步游标；
- Storage 只保存头像等小文件；第一阶段不上传 MP3/MV；
- 本地 SQLite 继续作为主库，新增待同步队列；断网时照常使用，联网后增量上传；
- 播放事件使用全局唯一事件 ID 追加，服务端去重，因此电脑与安卓产生的次数可以安全合并；
- 收藏和设置按字段更新时间合并，歌单项采用软删除，避免两台设备同时操作时整库互相覆盖；
- 数据表启用 Row Level Security，每条记录绑定 `user_id`，账号只能读取和修改自己的数据；
- 登录令牌放入系统安全存储，不写入普通设置文件。

这套架构可以同步听歌排行。周榜、月榜和总榜可以由云端播放事件实时聚合，也可以同步事件后在本地计算；后者离线体验更好，第一阶段优先采用。真正成本高的是 MP3/MV 的存储和下载流量，因此媒体云盘留到第二阶段，再评估 R2/S3 兼容对象存储、文件指纹去重和版权边界。

### 项目文件与版本保留约定

从本轮开始，Sona 以及后续软件开发项目统一采用“两代保留制”：每个平台与每种交付物只保留最新版本和上一版本。同一版本的 Windows 包、Android 通用 APK、分架构 APK 与源码包属于同一代，可以同时保留。新版本完成检查、测试与构建后，再清理第三新的版本，以便既控制目录体积，也始终保留一个可回退版本。

### Sona 0.3.4：液态控制层、有效播放事件与背景图库

这一版完成了此前确认的播放器视觉和数据规则返工。

#### 唱片不再是一张“唱臂贴歪的合成图”

唱片本体改为原创生成的顶视图素材 `assets/vinyl/premium_vinyl_v2.png`：黑色唱片、细密沟槽、象牙白中心标签和真实径向高光。生成时先使用纯洋红色背景，再在本地去除背景并验证透明通道；最终素材已经复制进项目，不依赖生成工具的缓存目录。

最终生成提示词的核心约束是：正上方正投影视角、单张完整黑胶、纯色抠图背景、没有唱臂和唱机底座、没有文字与品牌。唱臂不再烘焙进图片，而是由 Flutter 画布单独绘制，按“右上转轴—弯臂—外圈唱针”的几何关系定位。这样唱片可以独立旋转，唱臂保持静止，也能随桌面和手机尺寸等比缩放。

#### 液态玻璃的使用边界

根据 Apple Human Interface Guidelines 的 Materials 说明，Liquid Glass 应作为浮在内容之上的控件与导航层，并且要克制使用；内容背景本身不应全部玻璃化。因此 Sona 只对搜索框、筛选器、播放器信息面板和临时音量条使用小范围模糊、半透明渐变、亮边、内高光和柔和阴影，没有对整张 MV 或整个歌曲列表执行高开销模糊。

参考资料：

- https://developer.apple.com/design/human-interface-guidelines/materials
- https://developer.apple.com/videos/play/wwdc2025/219/

完整播放器和底部常驻播放器的主播放键、上一首、下一首与音量键都重新放大并调整间距；主播放键和非静音音量状态会跟随当前背景的强调色。全屏播放器继续使用竖向液态玻璃音量条，底部桌面播放器保留横向滑杆和百分比，避免为了统一外观破坏常用操作。

MV 画面现在也是播放控制区：单击视频可暂停，再单击继续。播放器信息面板仍保留独立播放键，键鼠和触屏都可以选择顺手的入口。

首页原先突兀的“曲库 248.5 MB”改为带存储图标、细边框和主题色的小型数据胶囊。它仍然只表达实时容量，不伪装成跳转按钮。

#### 自定义背景从单槽位升级为持久图库

旧逻辑在切换内置皮肤时清空 `appearance.custom_path`，因此用户刚导入的图片会从选择器消失。新状态模型把“当前正在使用的背景”和“已经导入的背景列表”拆成两个概念：

- 切换内置皮肤只取消当前自定义背景，不删除导入记录；
- 最近 5 张自定义背景以 JSON 索引保存在本地设置表；
- 每张背景保存自己的主色调，重新选择时会同步恢复边框、按钮和进度条强调色；
- 文件继续位于 Sona 本地数据目录，不上传网络。

#### 有效播放次数与数据库版本 5

点击歌曲不再立即增加排行次数。播放器会记录真正连续播放过的媒体秒数，并把听过的秒区间去重：拖动进度条跳过的部分不计算，来回重复播放同一小段也不会重复覆盖计时，暂停期间不增加。

- 不超过 10 分钟：听过 50%，且普通歌曲至少 30 秒，记 1 次；
- 少于 30 秒的短音频：完整播放可以记 1 次；
- 超过 10 分钟的长音频或 MV：实际听满 5 分钟记 1 次；
- 同一次播放会话最多生成一条有效事件。

数据库升级到版本 5。`play_events` 新增唯一 `event_id`、实际听歌毫秒数和媒体总时长。唯一事件 ID 是未来多设备云同步时去重的基础：Windows 和 Android 即使重复上传同一条事件，云端也只能插入一次。

#### 云同步到底贵不贵

### Sona 0.3.5：细长音量层、稳定拖动与媒体识别路线

这一版先处理三个已经确定的交互问题，没有把尚未商定的联网识别偷偷塞进软件。

#### 浅色背景下，选中状态不再依赖白字

听歌排行的“近 7 天 / 本月 / 总排行”属于分段选择器。旧主题只改变边框和浅色背景，没有显式规定选中文字颜色，Flutter 默认状态色在部分主题下会变成白色，导致浅底上几乎看不见。现在所有同类分段按钮统一采用深色高对比文字，选中项使用更粗字重、主题色浅底和更明显的主题色边框。这样既醒目，也不会再通过刺眼的纯色大色块抢内容。

#### 进度条为什么会在松手后闪回旧位置

拖动期间，界面使用一个临时预览值；旧实现一松手就立刻清空预览值，然后才异步通知播放器跳转。播放器需要短暂时间完成 seek 并回传新进度，在这段间隙中，滑块只能重新显示旧进度，于是肉眼看到一次闪回。

现在全屏播放器和底部常驻播放器采用同一规则：松手后继续固定显示用户选择的目标位置，等待播放器完成跳转并留出极短的状态传播时间，再交还给实时进度流。它不是用动画掩盖问题，而是消除了两个异步状态之间的空窗。

#### 为什么写了 72 像素，音量层却还是大胖方块

旧音量层的内容容器虽然只有 72 像素宽，外层却使用 Flutter `Dialog`。桌面端 Dialog 自带最小宽度约束，因此内容被强制撑宽。0.3.5 移除 Dialog，改用没有最小宽度的通用浮层、右侧对齐、58 像素宽的液态玻璃容器，并保留百分比、竖向滑杆和点击静音。弹层仍可点击外部关闭，但真正成为细长竖条。

#### 当前“封面首字母”到底是什么

当前版本还没有从网络识别封面。占位封面的文字来自歌曲标题中第一个可用的中文、英文字母或数字；背景渐变根据文件内容哈希稳定选择。因此同一个文件重新启动后样式不会乱变，但它只是一张可辨认的占位卡，不代表真实专辑封面。音频导入目前会读取已有的标题、歌手、专辑和时长标签；没有标签时使用文件名，视频目前主要使用文件名。

#### 歌名、歌手和封面识别不能只靠一个“万能 AI”

Sona 适合采用分层识别，并且所有结果先预览、后确认，只写入 Sona 数据库，不直接改原文件：

1. **本地零成本层**：优先读取 MP3/FLAC/M4A 的 ID3、Vorbis 或 MP4 标签和内嵌封面；没有标签时解析常见文件名，例如“歌手 - 歌名”“《歌名》 歌手”和视频标题中的歌手、书名号与清晰度噪声。这一步快速、离线、没有隐私问题。
2. **音频指纹层**：用 Chromaprint 在本地把音频变成较小的声音指纹，再查询 AcoustID 与 MusicBrainz，获得候选录音、歌名、歌手和专辑。它不是让大模型听整首歌，也不需要上传原始 MP3/MV。MusicBrainz 官方说明，Picard 正是先用 `fpcalc` 生成指纹，再通过 AcoustID 查找匹配录音。
3. **困难媒体层**：演唱会、翻唱、串烧、变速、现场噪声和很长的 MV 可能与官方录音指纹不一致。MusicBrainz 也明确记录了卡拉 OK、伴奏版、剪辑版、短片段和明显时长差会造成误匹配或漏匹配。这类文件应该每隔一段时间取样，结合文件名、画面文字 OCR、音频候选和人工确认；串烧还可能需要识别成多个章节，不能强行猜成一首歌。
4. **商业识别层（可选）**：以后可以接入商业音乐识别服务处理更难的片段，但需要账号、API 密钥、网络请求和额度预算。它必须是用户主动点击的联网功能，而不是导入时默认上传音频。

建议下一阶段先实现“智能整理预览”：展示原标题、建议歌名、建议歌手、建议专辑、来源和可信度，支持批量勾选应用；随后再加入可选的 AcoustID / MusicBrainz 联网识别。歌手分类页应建立在已确认的数据上，避免错误识别把曲库分得更乱。官方参考：

- https://musicbrainz.org/doc/AcoustID
- https://picard-docs.musicbrainz.org/en/latest/tutorials/acoustid.html
- https://musicbrainz.org/doc/Guides/AcoustID

### Sona 0.3.6：控件锚定、模式幂等与 MV 时长回填

#### 音量条为什么“细了但还是歪”

0.3.5 把音量弹层从系统 Dialog 改成了真正的细长浮层，但定位仍然依据整个屏幕右侧，而不是用户点击的音量按钮。因此播放器面板改变宽度或位置后，弹层会漂到玻璃面板边缘，与音量图标不在同一条竖线上。

0.3.6 改为锚点定位：点击时读取音量按钮在屏幕中的真实坐标，以按钮中心作为水平中轴，把 58 像素宽的竖向音量条放在按钮正上方；同时根据窗口边界执行夹取，避免手机窄屏或窗口边缘发生溢出。弹层的缩放动画也改为从底部中心展开，视觉上与按钮保持一条直线。

#### 已经选中的模式不应该再次执行切换

旧版“唱片 / MV”胶囊即使处于选中状态仍能点击。再次点击“MV · 已配对”会重新执行视频模式切换，播放器重新打开媒体后进度回到开头。现在模式按钮遵循幂等原则：点击已经选中的模式不执行任何操作；点击另一个未选中的模式才切换。没有配对 MV 时，“关联 MV”仍然可以点击并进入选择流程。

#### 为什么所有独立 MV 都显示 0:00

导入器原本只对音频调用标签读取器；遇到视频文件时直接跳过元数据读取，并把时长写成零。列表只是忠实显示数据库值，因此这不是格式化错误。

新逻辑分为两条：

- 新导入的视频使用 MediaKit 播放器内核以 `play: false` 静默打开，只读取时长，不播放声音、不创建视频窗口；
- 已经存在于曲库且时长为零的独立 MV，会在曲库加载完成后后台逐个探测，得到时长后立即更新界面并写回 SQLite，下次启动无需重复探测。

每个文件最多等待 6 秒。无法读取或文件已经移动时保留 0:00，不阻塞整个曲库。音频、已经有正确时长的媒体和 MP3+MV 配对记录不会被重复处理。列表中的媒体类型胶囊宽度也从 92 缩到 66 像素，为时长与右侧操作按钮留出更自然的间隔。

### 后台播放与通知栏的技术决定

Android 的后台音频不能只靠一个 UI 开关；正确实现需要 `MediaSessionService` 前台媒体服务、`FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限、系统媒体通知和媒体按键回调。这样通知栏/锁屏才会显示歌曲、播放暂停与上下首，并且应用退到后台时播放器不会被系统随意回收。

Sona 当前使用 `media_kit` 作为跨平台播放内核。下一步会在不替换该内核的前提下，为 Android 增加一层 MediaSession 适配；在实现完成前，不在设置里放会误导用户的「后台播放已开启」假开关。

### 0.3.14：移动端的主题统一、真正居中与分层返回

#### 底部导航为什么会出现一个莫名其妙的红色方框？

底部栏原本使用 `InkWell` 处理点击。虽然视觉上只给“选中项”绘制了小胶囊，但 Android 的键盘/焦点/点击状态仍可能由 Material 默认的 overlay 额外画出一块矩形色层，于是看起来像主题色的正方形框套在小胶囊外面。

0.3.14 显式关闭该控件的 splash、highlight、focus 与 overlay 色层；选中态不再作用于整项容器，而只作用于图标背后的 30 像素圆形。文字保留正常颜色和字重，因此导航的层级只由一个小圆点表达，不会再有“选中一大块”的效果。

#### 播放器的主题色不应该只改播放键

移动播放器之前收藏心形使用了固定粉红色；这会让蓝色晴海、金色农场等皮肤下出现不属于主题的突兀色。现在收藏激活态和循环激活态都读取当前主题的 accent。播放/暂停按钮由 `Stack` 的中心层单独定位，不再受左右按钮数量影响：左右控制再多，播放键依然对齐信息面板的水平中心。

#### 安卓侧滑返回的层级

Android 的返回手势不能一律关闭页面。曲库/歌单详情进入多选后，第一次侧滑现在会先退出多选并清空临时勾选；只有不在临时操作状态时才关闭当前页面或抽屉。Android Manifest 同时开启预测返回回调，使这个逻辑能接入较新的 Android 系统返回手势。

### 0.3.15：控制栏视觉配平与手机端排行入口

#### “居中”不只是把播放键放在中线

上一版用绝对居中保证了播放键的位置，但左边只有循环、上一首两个控件，右边有下一首、队列、收藏三个控件；几何中心正确，视觉重量却仍然向右偏。0.3.15 改用左右各三个等宽槽位：左侧是循环、上一首、一个不可见占位槽；中间固定播放/暂停；右侧是下一首、队列、收藏。左右栏宽度和图标间距完全一致，中心按钮仍保持正中，同时整体不再显得一边挤、一边散。

#### 为什么主题很浅时导航文字不能用白色？

#### 返回不再靠每个页面临时猜

这一版把 Android 返回行为划成四层，并逐项枚举了工程中所有 `Navigator`、弹窗、底部抽屉与 `PopScope`：

1. 临时状态：曲库或歌单正在多选时，第一次返回只退出多选并清空勾选；

数据库现在包含：

- `profiles`：显示名称与头像路径；
- `music_spaces / space_members`：一个账号的私人音乐空间，以及以后多个账号共同使用曲库的成员关系；
- `cloud_tracks`：歌曲元数据、内容哈希与可选的音频/MV对象路径；

第一阶段只同步账号、头像、歌单、收藏、排行与设置。这些都是很小的数据库记录，个人使用通常可从免费额度起步。MP3/MV 属于大文件和大流量，放在第二阶段单独启用；这样即使云端暂时没有配置，本地曲库仍是完整且可恢复的主数据。

## Sona 0.4.1：排行修复与第一版真正云同步（完成）

### 听歌排行为什么会整页变黑、字号失控

问题与 Supabase 无关。排行数据一直来自本地 SQLite，旧页面在桌面端作为主框架里的子组件使用没有问题，但手机端通过独立路由打开时，缺少自己的 `Scaffold`、Material 表面和主题背景。结果是页面继承不到正确的文字、卡片与背景约束：深色文字落在黑底上，空状态容器又被父布局拉满，于是出现截图中的巨型灰块。

0.4.1 为手机排行页增加独立页面骨架，并继续复用皮肤背景；空状态改成靠上、按内容收口的浅薄荷卡片。近 7 天、本月、总排行仍从同一批有效播放事件计算，播放达到歌曲总时长 70% 才计一次，短时间反复点击不会刷高次数。

### 这次云同步真正同步了什么

本版加入手动触发的双向同步。登录后点击“立即同步”，Sona 会先读取本地 SQLite，再与 Supabase 中属于当前账号音乐空间的数据比较：

- 账号：邮箱密码认证、显示名和头像；头像存入私有 `sona-avatars` 对象桶。
- 歌曲：标题、歌手、专辑、时长、媒体类型、收藏状态、播放次数和最后播放时间。
- 媒体：本地 MP3/音频与已配对 MV 上传到私有 `sona-media`；另一台设备缺少文件时下载到自己的 Sona 数据目录。
- 去重：先计算文件内容哈希，同一文件换了文件名也不会重复上传。
- 歌单：名称、描述、歌曲成员和顺序双向恢复；同名本地歌单优先，避免无提示覆盖。
- 排行：上传有效播放事件，而不是只上传一个总数。因此另一台设备也能重新计算近 7 天、本月和总排行。
- 设置：当前先同步内置皮肤标识；自定义背景原图、歌单封面等个性资源仍属于后续扩展，不在本版冒充“已经全同步”。

同步是“本地优先且不改原文件”：上传、下载或网络失败都不会删除电脑/手机中的原始歌曲。大文件超过当前免费项目的单文件限制时会跳过，并在同步结果里明确提示，而不是卡死整个同步任务。

### 为什么播放事件需要第二条数据库迁移

同一台设备可能重复点击同步。如果只把每次播放直接插入云表，第二次同步会再次插入相同记录，排行会虚增。0.4.1 为每条本地播放事件增加稳定的 `client_event_id`，云端建立唯一索引；重复上传同一个事件会被识别为同一条记录。

需要在 Supabase SQL Editor 再运行一次：

```sql
alter table public.play_events
  add column if not exists client_event_id text;

create unique index if not exists play_events_user_client_event_idx
  on public.play_events(user_id, client_event_id)
  where client_event_id is not null;
```

即使暂时没运行这条 SQL，账号、头像、媒体、收藏、歌单和累计播放数仍可同步；只有“逐条播放历史跨设备恢复”会被安全跳过并显示提醒。

### Supabase 到底能放多少首歌

按 2026 年 8 月 Supabase 官方页面，Free 方案为 0 美元，项目包含约 500 MB 数据库、1 GB 文件存储、5 GB uncached egress 与 5 GB cached egress，并允许 5 万月活用户；免费项目连续一周无活动可能暂停。数据库里存歌名、收藏和排行非常省空间，真正占额度的是 MP3、封面与 MV 文件。

以 1 GB 文件空间粗略估算：

- 普通 8–12 MB MP3：理论约 80–125 首，给头像、封面和余量后按 70–100 首更稳妥。
- 15–25 MB 高码率歌曲：约 40–65 首。
- 100–500 MB MV：存储角度只能放约 2–8 个；更关键的是 Free 方案单文件上传上限约 50 MB，因此多数完整 MV 在免费档根本不能上传。
- 下载流量也会消耗额度：1 GB 曲库在多台设备反复完整恢复 5–10 次，可能比存储更早触及当月流量限制。

因此当前策略很现实：小型私人 MP3 曲库可以从免费档开始；大量 MV 不适合把 Supabase Free 当网盘。Pro 当前从 25 美元/月起，包含更高的文件、数据库和流量额度，但现阶段没有必要急着升级。官方资料：

### 云端额度、账号隔离与删除后是否回收空间

可以把当前的 Supabase 项目理解成一栋“小型共享仓库”，而不是每个账号各自免费获得一栋新仓库。`sona-cloud` 这个项目有一份项目级总额度；所有使用这个项目的 Sona 账号上传的数据库记录、头像、MP3 和 MV 都会共同占用这份额度。

不过“共用额度”不等于“互相看得到”。每个账号登录后都会拿到自己的身份凭证；数据库中的 `user_id`、音乐空间 `space_id` 和 RLS（行级安全规则）共同决定该账号能读写哪些行。默认情况下，A 账号只能看到自己的资料、收藏、播放记录和所属音乐空间中的歌曲；B 账号即使知道项目地址，也不能直接读取 A 的私有数据。以后如果要做“两个账号共同使用同一个曲库”，才把它们同时加入同一个 `music_space`，这是一项明确授权，不是自动共享。

例子：若项目只有 1 GB 文件空间，甲上传 10 首歌、乙上传 20 首歌、丙上传头像和 MV，它们会一起消耗这 1 GB；不存在“每人额外 1 GB”。目前只给两三个人使用时，主要看总媒体文件大小即可，数据库中的歌名、收藏和排行记录占用极小。

删除后可以重新获得容量，但要分清两层：

1. 从歌单删除，只是取消歌单成员关系，不会删除云端歌曲文件，也不会释放容量。
2. 从曲库执行“删除云端媒体”时，才应同时删除数据库中的曲目记录与 Storage 中的 MP3/MV 对象；对象真正删除后，项目占用空间会下降，新歌曲可以继续上传。
3. 仅删除本机文件不会自动释放云端空间；反过来，仅删云端文件也不会删你的电脑/手机原文件。Sona 的同步逻辑以保护原文件为先。

当前 0.4.1 已实现上传、恢复和去重，但还没有在界面上开放“删除云端媒体”按钮，避免误删。后续做这个功能时应使用两段确认：先说明将释放多少空间，再确认“仅删云端 / 同时从本机曲库移除”的范围。

### 注册页为什么要有确认密码与“小眼睛”

Sona 的“注册”调用的是 Supabase Auth 的真实邮箱密码注册接口：账号会在 Supabase 的身份系统中创建，密码只以不可逆哈希形式由认证服务保存，Sona 客户端、数据库表和开发者都不应看到或保存你的明文密码。若项目开启邮箱确认，Supabase 会向该邮箱发送验证邮件；验证完成后才允许以该邮箱登录。因此填写可收信的真实邮箱即可，不能随便写一个收不到邮件的地址。

确认密码与显示/隐藏密码是客户端体验与防错层，不是云端额外保存一份密码：注册时先比较两次输入是否完全一致，再把其中一份通过 HTTPS 交给认证服务；登录页则只需要一份密码。0.4.1 起，注册页包含“密码 / 确认密码”、至少 8 位校验、基础邮箱格式校验，以及眼睛图标切换明文显示与黑点遮罩；密码输入关闭系统联想与自动纠错，减少手机键盘擅自改动密码的风险。

### 下一阶段账号体验：用户名注册，邮箱作为安全绑定

产品方向确定为：注册时只需“唯一账号名 + 密码 + 确认密码”；邮箱不是强制门槛，但在设置中可绑定。绑定邮箱后，它才成为找回密码、接收安全提醒与改绑验证的凭证。登录框接受“账号名或已绑定邮箱 + 密码”。这比一开始强迫私人用户填邮箱顺手，也避免随便填一个收不到邮件的地址却误以为能找回账号。

需要注意 Supabase Auth 的原生密码登录只接受邮箱或手机号，不直接接受自定义账号名。因此 Sona 要实现“账号名登录”不能把密码存在 `profiles` 表里，更不能在客户端保存管理员密钥；正确做法是增加受控的 Supabase Edge Function（小型后端）：

1. 注册函数校验账号名唯一，创建 Auth 用户并建立 `profiles.username` 映射；密码仍交由 Supabase Auth 哈希保存。
2. 登录函数接收“账号名或邮箱”，账号名先在服务端映射到对应 Auth 身份，再走正常的密码校验；客户端始终只拿到自己的登录会话。
3. 初次绑定邮箱：输入邮箱 -> 给该邮箱发 6 位一次性验证码 -> 验证成功才写入 `verified_email`。
4. 改绑邮箱：先向旧已绑定邮箱发送验证码；旧邮箱验证成功后，输入新邮箱并再验证新邮箱；两个步骤完成才替换绑定。
5. 忘记密码：输入账号名或邮箱，若存在已验证绑定邮箱则发送验证码；验证成功后才允许设置新密码。

验证码不能明文存储。后端应只保存验证码哈希、用途、目标账号、10 分钟过期时间、尝试次数和重发冷却；验证成功立即作废，并对“账号是否存在”的错误信息做模糊化，防止被用来批量猜账号。发送邮件将需要配置可靠 SMTP/邮件服务；Supabase 自带试用邮件服务适合开发，但官方目前有很低频率限制（约每小时 2 封），不适合真实多人验证码流程。

这条方案比默认邮箱登录多一层 Edge Function 与验证码表，但体验正好符合 Sona：不绑邮箱仍可本地/云端使用；绑定后才解锁可恢复、可改绑的真正账号安全能力。开始实现前需要决定验证码邮件服务（例如 Resend、Brevo 或自己的 SMTP），因为这涉及外部账号与可能的邮件额度。

### 0.4.2：用户名 + 密码的第一阶段实现

本阶段先实现不依赖邮件服务的账号核心：注册页面改为“账号名 + 显示名称（可选）+ 密码 + 确认密码”，账号名必须是 3–24 位、以字母开头、只允许小写字母/数字/下划线；数据库 `profiles.username` 建立不区分大小写的唯一索引。登录框接受“账号名或已绑定邮箱”，退出登录只清除云端会话，不会删除本地曲库。

Supabase 原生密码认证底层要求邮箱或手机号码，而用户名本身不能直接作为密码身份。本阶段采用受控的内部认证地址：账号名 `sona_user` 会在 Auth 中映射为不可投递的 `sona_user@accounts.sona.local`，实际密码仍由 Supabase Auth 哈希验证；可见资料、音乐空间、收藏、歌单和播放事件全部仍由 Auth UUID 对应，不是靠用户名文字直接隔离。这样可先完成纯用户名体验，同时不给用户伪造一个“可用于找回密码”的邮箱。

因此在 Supabase 后台启用用户名注册前，应关闭 Email Provider 的 `Confirm email`：内部认证地址不能收邮件，若仍强制确认，注册会停在待验证状态。后续“绑定真实邮箱”功能会使用独立验证码表与受控邮件流程，而不是把这个内部地址展示给用户。等真实邮箱绑定上线后，登录框中的“已绑定邮箱”才对新账号可用；当前它兼容旧版已经用真实邮箱注册的账号。

执行顺序：先在 Supabase SQL Editor 运行 `202608150003_username_accounts.sql`，再安装 0.4.2。若 SQL 还没运行，新注册用户能建立 Auth 账号但云端资料触发器无法保存用户名，因此不能把新版本与旧数据库模式混用。

### 0.4.3：注册状态、邮箱确认与键盘避让的修正

实机反馈确认了一个不能“悄悄忽略”的认证配置冲突：当前项目的 `mailer_autoconfirm` 为 `false`，即 Supabase 仍要求邮箱确认；但 Sona 的第一阶段用户名注册使用的是内部不可投递地址 `账号名@accounts.sona.local`。这样点击注册时，Auth 可能创建一条“未确认用户”记录，但不会返回登录会话；之后再用同一账号名/密码登录就会得到 `invalid_credentials`。这不是歌单、排行或本地数据的问题，也不是用户密码被数据库读错了，而是认证状态没有完成。

0.4.3 的处理原则：

- 注册没有拿到登录会话时，视为失败，不再把它显示成“注册成功”或默默关闭弹窗。
- 把 `invalid_credentials`、账号占用、配置不兼容等原始英文异常转换为可执行的中文提示。
- 当前用户名方案必须在 Supabase `Authentication → Sign In / Providers → Email` 中关闭 **Confirm email**。若此前已经用某账号名触发过未确认注册，需要在 Supabase 的 **Authentication → Users** 删除那条未确认用户，再重新注册；否则这个账号名会一直被占用。
- 这一步不会降低未来“绑定真实邮箱”的安全性。真实邮箱绑定、找回密码、改绑邮箱会走单独的验证码流程；那时再开启邮件服务，而不是把内部认证地址当作用户邮箱。

同时，登录/注册弹窗采用“键盘避让 + 柔和过渡”：用系统键盘高度驱动 `AnimatedPadding`（240ms，`easeOutCubic`），表单内容可滚动，底部取消/提交按钮不会压住确认密码输入框。详细的可复用规范见桌面文件 `Sona键盘避让与柔和过渡动效规范.md`。

### 0.4.4：认证开关与键盘避让的二次校正

实机验证时发现 Supabase 的 Email 设置有两个不同开关，不能混为一谈：

- **Enable email provider**：总开关。关掉后，任何邮箱/密码注册都会报 `Email signups are disabled`，即使 Sona 用的是内部认证地址也无法注册。
- **Confirm email**：确认开关。对当前“用户名 + 内部认证地址”的过渡方案应关闭；否则内部地址无法收信，账号会停在未确认状态。

本项目需要的组合是：**Enable email provider = 开启；Confirm email = 关闭**。软件会把“注册入口被关闭”翻译为明确中文并指出路径。

另外，0.4.3 的键盘动画错误地在 `AlertDialog` 自带避让之外又叠加了基于键盘高度的 `AnimatedPadding`，两次上移导致弹窗被顶到屏幕上方。0.4.4 移除额外位移，交回 Material `AlertDialog` 的原生键盘避让；表单仍为可滚动布局，避免按钮和确认密码重叠。若以后改用自定义 `Dialog`，再由它单独控制 240ms / `easeOutCubic` 的缓动，绝不重复叠加。

### 0.4.5：头像裁切、缓存规避与紧凑歌单编辑

头像现在和背景、歌单封面采用同一套交互：先选取本地图片，再进入固定 **1:1** 的裁切框；用户可拖动图片、缩放并决定保留区域，确认后再上传。裁切结果统一编码为 JPEG，避免不同设备保存透明 PNG、HEIC 等格式时显示不一致。

此前“已上传但仍显示默认头像”主要是对象路径固定导致的缓存问题：同一 URL 下替换文件后，设备或 CDN 可能短时间继续返回旧图片。0.4.5 改为每次头像更新都生成带时间戳的新对象路径，资料表先切换到新路径，确认成功后再异步清理旧头像。因此另一个设备登录同一账号并点击同步后，会读取到全新的头像地址，不会被旧缓存卡住。

新建/编辑歌单同步收紧了封面尺寸、描述行数与间距：封面缩至 88px，描述默认只保留一至三行，减少封面下方无意义的大面积留白，让名称、封面、描述与底部操作区更接近 LocalSend 的“内容决定容器高度”原则。

本版验证：`flutter analyze` 无问题，`flutter test` 7 项全部通过；Android ARM64 已安装为 **0.4.5 (2024)**，Windows x64 Release 同步构建完成。

### 0.4.6：头像真正回显、同步提示去技术化与圆润控件

这一版把“头像已经上传但仍显示默认图标”的链路改成可验证的闭环：裁切后的图片先上传到私有 `sona-avatars` 桶，再以当前账号 UUID 为主键 **upsert** 到 `profiles.avatar_path`，并要求数据库返回刚写入的资料。随后客户端只为这个刚上传的新文件生成签名访问地址，立刻用该地址回显头像；旧头像文件则在新资料写入完成后异步回收。这样不会再出现“数据库其实没有更新，但界面先提示成功”的假成功状态。

资料读取也被拆成两层：先读账号资料，再单独尝试生成头像签名地址。即使旧头像文件被删掉或网络短暂失败，账号名称、云连接状态和同步按钮仍然可以正常显示，错误不会把整张账号卡一起吞掉。

同步说明改成用户语言：现在会直接说明“收藏、歌单、播放记录和小于 50 MB 的音乐可在已登录设备间同步；本地原文件仍保留在本机”。同步结果只报告上传、恢复和排行是否完成，不再把“第几条 SQL”这种开发过程暴露给使用者。

移动端的导入按钮和曲库筛选栏也统一为圆角胶囊：导入按钮使用当前皮肤的强调色并降低饱和度，筛选项不再使用系统分段控件的直角中间块，而是每个状态都保持独立的圆润选中面。这延续了 LocalSend 风格中“克制强调色 + 大圆角 + 单一主操作”的原则。

本版本在构建前执行 `flutter analyze`，结果为无问题；`flutter test` 7 项全部通过。

### 0.4.8：账号主链路解耦、头像双重索引与同步幂等

实机暴露的 `Could not find the 'username' column of 'profiles'` 不是密码失效，而是客户端把“能否登录”和“能否读取资料表”绑成了一次操作：Supabase Auth 已经完成认证，但随后查询旧数据库结构失败，界面便把整个账号区域显示成失败。0.4.8 将两条链路彻底拆开：登录结果只由 Supabase Auth 决定；`profiles` 只负责显示名称和头像路径，即使资料表临时不可用，已经取得的会话仍然有效，用户可以正常退出、再次登录和同步数据。

用户所设想的 `X1 / X2 / X3` 在真实系统中对应 Supabase Auth 自动生成的 **UUID**。账号名和密码负责证明“你是谁”，但收藏、歌单、头像、播放记录与音乐空间都不直接用易变的账号名关联，而是统一引用这个不会改变的 UUID。改显示名称不会换身份；以后绑定邮箱也只是给同一个 UUID 增加登录/找回方式，不需要搬迁整套音乐数据。密码继续只由 Auth 安全校验，Sona 数据库不会存储明文密码。

当前用户名阶段仍在 Auth 内部使用 `账号名@accounts.sona.local` 作为适配地址，但该地址只属于技术实现，不是真实邮箱，也不再出现在账号卡、登录提示或同步结果中。界面优先显示用户填写的显示名称，其次显示账号名；所有数据库/API 原始异常都被转换为简短中文提示，避免再把 `PostgrestException`、状态码和表名暴露给普通用户。

头像采用“双重索引”保证换设备后仍能恢复：图片文件存放在私有 `sona-avatars` Storage；当前对象路径首先写入 Auth `user_metadata.avatar_path`，同时尽力镜像到 `profiles.avatar_path`。登录新设备时优先读取资料表，读取失败则回退到 Auth 元数据，并为私有文件生成临时签名地址。上传新头像时先生成带时间戳的新路径、确认新路径已经写入账号，再清理旧文件，避免 CDN 缓存和中途失败造成头像丢失。这样资料表升级不同步时，头像也不会拖垮登录主流程。

“立即同步”现在按幂等原则设计，同一个动作反复执行不会制造重复歌曲或虚增播放次数：

1. 曲目用 `space_id + content_hash` 作为唯一身份并执行 upsert；同一个音乐空间内，相同文件内容只更新既有记录。
2. 每次有效播放拥有稳定的 `client_event_id`，云端以 `user_id + client_event_id` 建立唯一约束并 upsert；手机和电脑重复上传同一事件仍只计算一次。
3. Storage 对象路径由音乐空间和内容哈希确定，上传使用覆盖式 upsert，不会因为点击两次同步生成两份相同媒体。
4. 下载前先比较本地内容哈希，只恢复本机缺少的曲目；同步永远不覆盖用户原始 MP3/MV 文件。

新建/编辑歌单的封面裁切仍固定为 **1:1**，0.4.8 同时把弹窗里的预览改成正方形，避免“裁切时是正方形、预览却是横长方形”的视觉误导。名称与描述继续采用并排布局，减少多余留白。

本版已完成 `flutter analyze`（无问题）、`flutter test`（7 项全部通过）、Android ARM64 Release 与 Windows x64 Release 构建。Android 实机已覆盖安装并确认版本为 **0.4.8 (2027)**；安装过程没有启动或弹出额外测试窗口。

### 0.4.7：歌单编辑的横向封面与并排信息布局
